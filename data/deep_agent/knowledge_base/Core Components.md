
# Core Components Analysis

## 1. Overview

The analyzed files form the core of the `instructor` library, a powerful tool that enhances AI model provider clients like OpenAI and LiteLLM. Its primary function is to enable structured data extraction from model responses by binding them to Pydantic models. This is achieved by "patching" the client's chat completion methods. The library introduces features like response model validation, automatic retries with re-asking capabilities, and a streamlined streaming interface for partial and iterable responses.

## 2. File-by-File Analysis

### `instructor/client.py`
- **Purpose**: This module serves as a backward-compatibility layer. It allows users to continue using old import paths (`from instructor.client import ...`) while transitioning to the new `instructor.core.client` structure. It achieves this by lazily importing the core client components and issuing a `DeprecationWarning` upon access.

### `instructor/core/client.py`
- **Purpose**: This is the main user-facing module. It defines the `Instructor` and `AsyncInstructor` classes, which act as wrappers around the patched AI client. It provides the primary interface for making structured API calls.
- **Key Components**:
  - `Instructor`/`AsyncInstructor`: These classes wrap a patched `create` function. They provide methods like `create`, `create_iterable`, and `create_partial` which are the main entry points for users. They also manage global settings like default keyword arguments and hooks.
  - `from_openai()`/`from_litellm()`: These are factory functions that take a standard OpenAI or LiteLLM client and return a patched `Instructor` or `AsyncInstructor` instance, making the setup process straightforward.
  - `Response`/`AsyncResponse`: Helper classes that provide a simpler, input-centric API (`.create(input="...")`) for making calls without needing to construct the full message list.

### `instructor/core/patch.py`
- **Purpose**: This module contains the core logic that enables the library's main features. The `patch` function is the central piece of the entire library.
- **Key Components**:
  - `patch()`: This function is overloaded to accept either a client instance (like `openai.OpenAI`) or a callable (like `client.chat.completions.create`). It wraps the original `create` method with new logic that handles the `response_model` parameter, retries, and validation. It determines whether to apply a sync or async wrapper based on the original function.
  - `handle_context()`: A utility to manage the transition from the deprecated `validation_context` to the new `context` parameter.
  - `new_create_sync()`/`new_create_async()`: These are the wrapper functions created by `patch`. They intercept the call, process the `response_model` to modify API request parameters (e.g., adding tool schemas), handle templating, and then delegate the actual API call to the retry logic.

### `instructor/core/retry.py`
- **Purpose**: This module provides the robust retry mechanism for API calls. It is built on top of the `tenacity` library.
- **Key Components**:
  - `retry_sync()`/`retry_async()`: These functions wrap the actual API call within a `tenacity` retry loop. They catch `pydantic.ValidationError` and `JSONDecodeError` exceptions.
  - **Error Handling**: Upon catching a validation error, the logic can construct a "re-ask" prompt that includes the error details and sends it back to the model, giving it a chance to correct its output. This is a key feature for improving reliability.
  - `InstructorRetryException`: A custom exception raised when all retry attempts fail, bundling the last error, the final completion attempt, and usage statistics.
  - `initialize_retrying()`: A helper function to configure the `tenacity.Retrying` or `tenacity.AsyncRetrying` object with the specified number of attempts and total timeout.

## 3. Architecture & Data Flow

The data flow for a typical `create` call is as follows:

1.  **User Call**: The user calls `instructor_client.create(response_model=MyModel, ...)`.
2.  **`Instructor` Class**: The `Instructor` class receives the call and passes it to the patched `create` function that was generated by `instructor.patch()`.
3.  **`patch` Wrapper (`new_create_...`)**: The wrapper function in `patch.py` takes over.
    - It processes the `response_model` to generate the appropriate tool or function-calling schema for the AI model provider.
    - It updates the `kwargs` for the API call with this schema.
4.  **Retry Logic (`retry_...`)**: The call is passed to `retry_sync` or `retry_async` in `retry.py`.
5.  **API Call**: Inside the retry loop, the original, underlying `client.chat.completions.create` function is finally called with the modified arguments.
6.  **Response Processing**: 
    - If the API call fails (e.g., network error), `tenacity` retries the call.
    - If the call succeeds, the response is sent to `process_response`.
    - `process_response` attempts to parse the model's output (e.g., a JSON string) into an instance of `MyModel`.
7.  **Validation & Retry**: 
    - **Success**: If parsing and validation succeed, the Pydantic model instance is returned to the user.
    - **Failure**: If parsing or validation fails, a `ValidationError` is raised. The `retry_...` function catches this, potentially modifies the `kwargs` to include a re-ask message, and lets `tenacity` trigger a new attempt.
8.  **Final Failure**: If all retries are exhausted, an `InstructorRetryException` is raised.

## 4. Code Deep Dive

### The `patch` function

The `patch` function is the heart of the library. It dynamically wraps the AI client's method.

```python
# instructor/core/patch.py

# Overloaded signatures for type hinting
@overload
def patch(
    client: OpenAI,
    mode: Mode = Mode.TOOLS,
) -> OpenAI: ...

@overload
def patch(
    create: Callable[T_ParamSpec, T_Retval],
    mode: Mode = Mode.TOOLS,
) -> InstructorChatCompletionCreate: ...

# Implementation
def patch(
    client: OpenAI | AsyncOpenAI | None = None,
    create: Callable[T_ParamSpec, T_Retval] | None = None,
    mode: Mode = Mode.TOOLS,
) -> OpenAI | AsyncOpenAI:
    if create is not None:
        func = create
    elif client is not None:
        func = client.chat.completions.create
    else:
        raise ValueError("Either client or create must be provided")

    func_is_async = is_async(func)

    @wraps(func)
    def new_create_sync(...):
        # ... handle response_model
        # ... call retry_sync
        ...
    
    @wraps(func)
    async def new_create_async(...):
        # ... handle response_model
        # ... call retry_async
        ...

    new_create = new_create_async if func_is_async else new_create_sync

    if client is not None:
        client.chat.completions.create = new_create
        return client
    else:
        return new_create
```

This code showcases how `patch` replaces the original `create` method with a new version (`new_create_sync` or `new_create_async`) that adds the structured response handling.

### Retry with Re-ask Logic

Inside `retry_sync`/`retry_async`, the error handling demonstrates the re-asking mechanism.

```python
# instructor/core/retry.py

def retry_sync(...):
    # ... tenacity loop setup
    for attempt in max_retries:
        with attempt:
            try:
                response = func(*args, **kwargs)
                return process_response(
                    response=response,
                    response_model=response_model,
                    ...
                )
            except (ValidationError, JSONDecodeError) as e:
                # This is the key part for re-asking
                kwargs = handle_reask_kwargs(
                    kwargs=kwargs,
                    mode=mode,
                    response=response,
                    exception=e,
                    failed_attempts=failed_attempts,
                )
                raise e # Re-raise to trigger tenacity's next attempt
```

The `handle_reask_kwargs` function is responsible for modifying the chat messages to include the validation error, prompting the model to fix its mistake on the next attempt.

## 5. Integration Points & API Reference

- **Dependencies**: The core components heavily rely on `openai` for the client, `pydantic` for data modeling and validation, and `tenacity` for the retry logic.
- **Dependents**: Any part of an application that needs to interact with an LLM to get structured data is a potential dependent. The primary entry point is always an `Instructor` or `AsyncInstructor` instance.

### Public Interface

The main public interface consists of the factory functions and the methods of the `Instructor` classes.

| Function / Method | Signature | Purpose |
| --- | --- | --- |
| `from_openai` | `(client: openai.OpenAI, mode: instructor.Mode = ..., **kwargs) -> Instructor` | Creates a patched `Instructor` from an OpenAI client. |
| `from_litellm`| `(completion: Callable, mode: instructor.Mode = ..., **kwargs) -> Instructor` | Creates a patched `Instructor` from a LiteLLM completion function. |
| `Instructor.create` | `(self, response_model: Type[T], messages: list, max_retries: int = ..., **kwargs) -> T` | Makes an API call and returns a single Pydantic model instance. |
| `Instructor.create_iterable` | `(self, response_model: Type[T], messages: list, **kwargs) -> Generator[T, None, None]` | Makes a streaming API call, yielding a generator of Pydantic models. Used for `Iterable[T]` response models. |
| `Instructor.create_partial` | `(self, response_model: Type[T], messages: list, **kwargs) -> Generator[Partial[T], None, None]` | Makes a streaming API call, yielding partial Pydantic models as tokens arrive. |
| `Instructor.create_with_completion` | `(self, response_model: Type[T], messages: list, **kwargs) -> tuple[T, Any]` | Returns both the parsed Pydantic model and the raw API response object. |

*(Note: Async versions exist for all methods, returning `Awaitable` or `AsyncGenerator` types)*.
